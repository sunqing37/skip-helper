# 开发约束

## 代码与状态

- 沿用 Kotlin、Compose、Coroutines、StateFlow；UI 只发送明确意图，不直接模拟点击。
- 持久化实体使用 `@Serializable` 与 `@SerialName`，依赖生成 serializer；修改结构保留默认值/迁移策略，关注 release 混淆。不要用通配 keep 全项目掩盖问题。
- 新改代码避免无必要 `!!`、吞取消异常和空 catch。可预期失效必须有保守回退与原因；不要借性能优化扩大整库重构。
- 不重复维护状态或规则；暂不为单模块引入企业工程的依赖注入、网络与数据库体系。插件与依赖集中维护在现有 Gradle 文件；未进行 Version Catalog 迁移前不声称已经统一迁移。

## 性能

- 主线程不遍历完整控件树、不转换整帧截图、不读取磁盘。不得将 AccessibilityEvent/Node 长期缓存或传给不受控后台任务。
- 新异步入口要说明取消策略和过期结果判断。跨线程迁移不能只追求速度而跳过执行前复核。
- 会话限时、OCR 频率、节点/深度上限和日志上限不得默默删除；事件流必须限频/合并，不启动常驻轮询空转。
- Compose 中列表筛选/排序/分组用输入作为 remember key；日期格式器不要逐行逐次重组创建。缓存明确容量，持有 Application context。
- 性能结论给出代码路径或测量依据，静态发现不能冒充真机帧率/功耗结论。用户负责设备测试，不擅自运行 Perfetto、Monkey、压力操作或切换手机。

## 权限、数据与界面

- 所有应用及 OCR 默认关闭；不写系统授权数据库，不静默扩大范围。保活须显式开启并显示通知。
- 不记录、保存、上传截图或页面文字；日志仅包含包名、状态、计时与失败原因。不得添加联网权限或跨应用数据采集来“诊断”。
- UI 复用主题 token 和组件；保留深色模式、底部导航、真实配置状态与清晰错误提示。统计口径要明确，不伪造成功率、累计节省时间。
- 不新增自动化测试。必要的 Python 语法检查、脚本 dry-run 和 Java/Kotlin 编译属于工具验证，不得把它们当作真机验收。
